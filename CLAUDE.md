# Chips n' Dipshits

Multiplayer no-limit hold'em whose backend is a Google Sheet with an Apps Script web app. `README.md` has the setup, the house rules and the layout of the code; read it first.

## Commands

- `npm test`: unit tests, a few seconds. Run after every change.
- `npm run build`: type-checks all three TypeScript projects (Node, client, Apps Script) and builds `dist/`.
- `npm run test:e2e`: plays a full game in headless browsers, about a minute and a half. Run after any change to `src/client`, then look at the pictures it leaves in `screenshots/`.
- `npm run dev`: the game on localhost with tables in memory.
- `npm run deploy`: pushes the build to Apps Script. Outward-facing: only when asked.
- `npm run check:live`: plays a short game at the deployed address. Run after every deploy; it adds a table to the real Sheet.

## How the code is written

- TypeScript is run directly by Node, so imports carry the `.ts` extension, type imports use `import type`, and there are no enums or constructor parameter properties.
- `src/engine` stays pure: no `Date`, no `Math.random`, no I/O. Time and randomness arrive in `Ctx`. The table state must survive `JSON.stringify`.
- A hand can be on more than one board from its first card. A rule that deals, shows or pays goes through `src/engine/boards.ts` and every board in `hand.boards`, and never takes it that there is one board or that a second comes only after an all-in.
- Every rule change comes with a test in `tests/hand.test.ts` or `tests/table.test.ts`, and `tests/simulation.test.ts` must keep passing: it plays random games and checks that no chip is ever created or lost.
- What must hold of a table at every moment is in `tests/invariants.ts`, and `assertInvariants` is what the simulation, the saved-table test and the browser rig all call. Chips that can sit somewhere new go in its `CHIP_PLACES`.
- A table setting is a field of `TableConfig` and its entry in `CONFIG_SPECS` (`src/engine/config.ts`), plus a line in `CONFIG_RULES` when it must agree with another setting. The defaults, the checks, both forms, presets and the simulation's random tables are read from there. `atCreate: 'only'` makes one that is chosen when the table is created and can't be changed after. A preset keeps every setting unless its entry says `inPresets: false`, for one that belongs to a single table or should not be readable by anyone with the game's address. A saved preset may predate or outlive any setting, so it is only ever read through `fromPreset` (`src/engine/presets.ts`).
- An amount is a whole number of the table's smallest unit: 150 is 1.50 at a table that plays cents. It is written out only by `formatAmount(amount, table)` and its variants in `src/engine/amounts.ts`, and a typed one is read only by `parseAmount(typed, table)`; never `String`, `toLocaleString` or `Number` on an amount. A form field for an amount is `amountField`, read with `amountOf` (`src/client/render/forms.ts`).
- A command is a member of the `Command` union, a handler in the module of `src/engine/commands/` for who may send it (`seat.ts`, `play.ts`, `host.ts`, `anyone.ts`) and a line in `HANDLERS` (`commands/index.ts`), with an entry in `FUZZ_COMMANDS` (`tests/randomPlay.ts`) so the simulation sends it and one in `DECLARED` (`tests/commands.test.ts`). A host's command declares `by: 'host or cohost'` or `by: 'host alone'`; on the page, `hostOrCohost` and `hostAlone` (`dialogs/dialog.ts`) decide who is offered it.
- Chips a rule makes a player put in before the cards are entries in the list `forcedBets` builds (`src/engine/forcedBets.ts`): a name in `Post`, who, how much, and `as: 'live' | 'contribution' | 'dead'`. `startHand` posts the list and nothing else: the play-by-play, the events, the replay and the pots follow from the entries, and the betting starts from the biggest live one (`openingBet`).
- Something that happens in a hand is a member of `HandEvent` (`src/engine/events.ts`), recorded with `record(hand, [...])` in `hand.ts` beside its line of narration, with a case in `replayHand` that plays it back. An event never holds a face-down card.
- What kind of hand is dealt is decided once, by `claimBombPot` in `src/engine/bombPots.ts`, before `forcedBets`. A rule that depends on the kind reads it from the hand (`hand.bombPot`), never from the settings, which may have changed since the deal.
- A night ends only in `endNight` and starts again only in `restartNight` (`src/engine/night.ts`). What happens when a night ends goes in `endNight`, and the end leaves the engine as a `nightEnded` effect and reaches the page as `TableChange.nightEnded`.
- A view sent to a player never contains another player's face-down cards, the deck, or anyone's token. `viewFor` is the only place views are built.
- The client redraws a part of the screen only when what it shows has changed (`Slot`), so a tap or a half-typed bet survives updates from the server.
- `App` (`src/client/app.ts`) is the screens. `TableConnection` (`connection.ts`) is the conversation with the server about one table: the poll that is kept open, sending commands, the lock on the move buttons, and which of the views that come back is the one to show. It tells `App` what happened through `TableListener` and never touches the page.
- A request that got no answer is not a refusal. Only `unauthorized` or `not_found` may take a player's seat out of the address or the browser's memory; anything else is retried. A move (`MOVES` in `connection.ts`) that got no answer is looked up with a fresh poll, never resent.
- Every request and every answer carries a build id, so a page from before a deploy can tell. The page asks only through `ServerLine` (`connection.ts`), never `platform.transport`. A host answers only through `BuildGate` (`src/server/build.ts`), and puts the build on any answer it makes up itself (the `internal` failure in `gas/main.ts`). A new operation gets its line in `OPEN_TO_ANOTHER_BUILD`: only one that changes nothing may be asked by a page of another build. Being out of date is `stale`, never `unauthorized` or `not_found`.
- `npm run test:e2e` also runs `scripts/hostedRun.ts`, which puts a stand-in for Apps Script's `google.script` in the page. Changes to how the page starts, remembers a seat or sends requests need a case there.
- Colors, fonts and radii in component CSS come from the tokens in `src/client/styles/tokens.css`, never a literal.
- CSS for a feature is its own file in `src/client/styles/`, with a line in `STYLESHEETS` (`styles/order.ts`), which is the order of the cascade. The build stops on a stylesheet that is not listed.
- A dialog is its own file in `src/client/render/dialogs/` that exports a `DialogKind`, its menu entry (`menu`) beside it, with a line in `REGISTERED` (`dialogs/index.ts`), whose order is the menu's. Dialogs open each other by kind (`handlers.open({ kind: 'ledger' })`), never by import.
- `styles/order.ts`, `dialogs/index.ts` and `effects.ts` are merged as a union (`.gitattributes`): when two branches each add a line at the same place, git keeps both and reports no conflict. Keep every entry and import in them on one line, and check the order of the list after a rebase that touched one.
- A choice a viewer makes for themselves is one entry in `PREFERENCES` (`src/client/prefs.ts`): its control in the Preferences dialog, where it is kept and its `data-` attribute or custom property on the app's element (`css`) follow from the entry. Read it with `prefs.get('sound')`, never from `Memory`.
- Something that happens on the page when the table changes (a sound, an animation, an alert) is a `TableEffect` in `src/client/effects/`, with a line in `TABLE_EFFECTS` (`effects.ts`), never a line in `App`. It reacts to everything its `TableChange` (`tableChange.ts`) hands it, the hand's new events (`events`) and the new chat and play-by-play lines (`feed`), and keeps no record of its own: that is where late, repeated and missed views are dealt with, and where a new list of things that happened gets the same treatment. What must be told once even past a late view (`nightEnded`) is remembered by `TableNews`, beside `tableChange`, never by the effect. What reaches the page more than ten seconds after it happened counts as missed and is handed to no effect, so a browser check lets the page show what happened before it moves the rig's clock on.
- Motion is decoration over a table already drawn as it truly is: it is played through `context.motion`, animates only transform and opacity, never delays a button, and once it lands or is cancelled leaves the page exactly as it is with animations off. What a hand event moves starts in the frame its sound does: `movesSeen` takes its beats from `soundsPlaced`, so the two are timed in one place.
- A field added to what a table saves gets its default in `SAVED_DEFAULTS` (`src/engine/upgrade.ts`), which fills in what a table saved earlier lacks; a setting needs only its registry entry. Any other change to the shape of `TableState` means bumping `STATE_SCHEMA` and adding the step to `upgradeState` that brings a table saved before the change forward. Either way `tests/savedTables.test.ts` must keep passing: it loads the tables older code saved (`tests/fixtures/tables/`) and plays them on.
- `scripts/rig.ts` sets up a table for a browser check with the cards fixed and a clock the check moves, and `scripts/screenChecks.ts` (run by `npm run test:e2e`) has one check per screen that has broken before. A new screen state, or a layout bug that gets fixed, gets a check there: `node scripts/screenChecks.ts "part of its name"` runs one.
- CI runs the browser tests too, with other fonts than a Mac has, so the buttons under the table wrap differently and the table gets another height and sometimes another shape. `RIG_FONT='Times New Roman' node scripts/screenChecks.ts` (narrower) and `RIG_FONT=Verdana` (wider) show here what fails only there; a check about the table's shape sets its height itself with `setStageHeight`.
- The rig's pages keep the table still. A check about motion opens one with `{ moving: true }`, waits on `dealt` (`.stage:not([data-moving])`), never on time, and measures it against a still page of the same table (`watch`).

## Google side

- `src/gas/sheetStore.ts` talks to the Sheet through small interfaces (`src/gas/sheets.ts`), with fakes in `tests/fakes.ts`. Every write and every cache refill happens under the script lock (`underLock`), which is what keeps the cache from ever being older than the Sheet. The fakes refuse a write, a new tab or a deleted row without it.
- A new tab of the Sheet is a store of its own: an interface in `src/server` named for what it keeps, with list-save-delete sized to what the service needs and the rule shared by both implementations beside it (`PresetStore` and `placeOf` in `presetStore.ts`); a memory implementation for `npm run dev`, the rig and the tests; and the Sheet's in `src/gas`, built on `openTab` and `underLock`. The deployed Sheet already exists, so the tab is made by `openTab(..., true)` on the first write, under the lock, and reading a Sheet without it is reading nothing. A row someone broke by hand is skipped, never fatal. Its limits go in the fakes (`rowLimits` for a cap on rows) and its tests in `tests/sheetStore.test.ts`, run against both implementations where the behavior is shared. Wire it in `src/gas/main.ts` and `ServiceDeps`.
- The fakes enforce the limits that bite (50,000 characters a cell, 100 KB a cache value, 250 characters a cache key); give them any new limit the store comes to depend on.
- Ledger entries and hand records are saved in the table's row with the state, then copied to their tabs. Only the write of that row may fail a request.
- Apps Script strips what it reads as comments from the page's inline scripts, and reads a `//` inside a template literal as one. `scripts/bundle.ts` ships the script with no `//` or `/*` in it and fails the build when it can't; the stand-in in `tests/appsScriptBundle.test.ts` strips the same way.
- `.clasp.json` and `.deployment.json` are per machine and ignored by git.
