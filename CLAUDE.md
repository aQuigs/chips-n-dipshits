# Chips n' Dipshits

Multiplayer no-limit hold'em whose backend is a Google Sheet with an Apps Script web app. `README.md` has the setup, the house rules and the layout of the code; read it first.

## Commands

- `npm test`: unit tests, a few seconds. Run after every change.
- `npm run build`: type-checks all three TypeScript projects (Node, client, Apps Script) and builds `dist/`.
- `npm run test:e2e`: plays a full game in headless browsers, about three minutes. Run after any change to `src/client`, then look at the pictures it leaves in `screenshots/`.
- `npm run dev`: the game on localhost with tables in memory.
- `npm run deploy`: pushes the build to Apps Script. Outward-facing: only when asked.
- `npm run check:live`: plays a short game at the deployed address. Run after every deploy; it adds a table to the real Sheet.

## How the code is written

- TypeScript is run directly by Node, so imports carry the `.ts` extension, type imports use `import type`, and there are no enums or constructor parameter properties.
- `src/engine` stays pure: no `Date`, no `Math.random`, no I/O. Time and randomness arrive in `Ctx`. The table state must survive `JSON.stringify`.
- A hand can be on more than one board from its first card. A rule that deals, shows or pays goes through `src/engine/boards.ts` and every board in `hand.boards`, and never takes it that there is one board or that a second comes only after an all-in. Ask for the number of boards (`hand.runs`, or `boards.length` in a record), never whether it is two.
- Every rule change comes with a test in `tests/hand.test.ts` or `tests/table.test.ts`, and `tests/simulation.test.ts` must keep passing: it plays random games and checks that no chip is ever created or lost.
- What must hold of a table at every moment is in `tests/invariants.ts`, and `assertInvariants` is what the simulation, the saved-table test and the browser rig all call. Chips that can sit somewhere new go in its `CHIP_PLACES`.
- A table setting is a field of `TableConfig` and its entry in `CONFIG_SPECS` (`src/engine/config.ts`), plus a line in `CONFIG_RULES` when it must agree with another setting. The defaults, the checks, both forms, presets and the simulation's random tables are read from there. `atCreate: 'only'` makes one that is chosen when the table is created and can't be changed after. A preset keeps every setting unless its entry says `inPresets: false`, for one that belongs to a single table or should not be readable by anyone with the game's address. A saved preset may predate or outlive any setting, so it is only ever read through `fromPreset` (`src/engine/presets.ts`).
- An amount is a whole number of the table's smallest unit: 150 is 1.50 at a table that plays cents. It is written out only by `formatAmount(amount, table)` and its variants in `src/engine/amounts.ts`, and a typed one is read only by `parseAmount(typed, table)`; never `String`, `toLocaleString` or `Number` on an amount. A form field for an amount is `amountField`, read with `amountOf` (`src/client/render/forms.ts`).
- A command is a member of the `Command` union, a handler in the module of `src/engine/commands/` for who may send it (`seat.ts`, `play.ts`, `host.ts`, `anyone.ts`) and a line in `HANDLERS` (`commands/index.ts`), with an entry in `FUZZ_COMMANDS` (`tests/randomPlay.ts`) so the simulation sends it and one in `DECLARED` (`tests/commands.test.ts`). A host's command declares `by: 'host or cohost'` or `by: 'host alone'`; on the page, `hostOrCohost` and `hostAlone` (`dialogs/dialog.ts`) decide who is offered it.
- A hand's button, who is dealt in and what each of them posts are decided in one place, `planHand` in `src/engine/handPlan.ts`, as data before a chip moves; `startHand` only carries the plan out. That module alone writes `buttonSeat`, `blinds` and what a seat owes. A rule about positions or who posts goes there, never in `startHand`.
- Chips a rule makes a player put in before the cards are entries in the list `forcedBets` builds (`src/engine/forcedBets.ts`): a name in `Post`, who, how much, and `as: 'live' | 'contribution' | 'dead'`. `startHand` posts the list and nothing else: the play-by-play, the events, the replay and the pots follow from the entries, and the betting starts from the biggest live one (`openingBet`).
- Something that happens in a hand is a member of `HandEvent` (`src/engine/events.ts`), recorded with `record(hand, [...])` in `hand.ts` beside its line of narration, with a case in `replayHand` that plays it back and in `placed` and `said` (`src/engine/replay.ts`), which make the steps of a replay and their lines; the build fails until all three have it. A move or an answer the engine gives for a player who was never on the clock for it says so in its event (`unasked`), so a replay puts nobody on the clock who was not. An event never holds a face-down card.
- A replay is the live table's renderer (`tableEl`) fed a view made on the page from a hand's record by `replayView` (`src/engine/replay.ts`): no second set of table components, no request but the one for the history, no sound and no motion. It never shows a card the record does not hold as seen, apart from the viewer's own from `DealtCards`, and a record never gains one.
- Before changing what a hand's record or an event holds, run `node scripts/goldenRecords.ts` and commit the files it writes: `tests/goldenRecords.test.ts` replays a hand from every schema, or finds it told as text.
- What kind of hand is dealt is decided once, by `claimBombPot` in `src/engine/bombPots.ts`, before `forcedBets`. A rule that depends on the kind reads it from the hand (`hand.bombPot`), never from the settings, which may have changed since the deal.
- A night ends only in `endNight` and starts again only in `restartNight` (`src/engine/night.ts`). What happens when a night ends goes in `endNight`, and the end leaves the engine as a `nightEnded` effect and reaches the page as `TableChange.nightEnded`.
- A view sent to a player never contains another player's face-down cards, the deck, or anyone's token. `viewFor` is the only place views are built.
- Who a member is on the list of players (`Member.identity`) is a label, never a key. Nothing that decides who may sit, act or see a card reads it. A member with none is an ordinary member everywhere. The id a hand record, the ledger or the night's numbers carry (`playerId`) is the member's, which is per table; the known player is `identity`.
- What a name may be and when two read alike is `src/engine/names.ts`, for a table's members and the list of players both. A rule about names goes there.
- The browser's memory of its player (`cnd.player`, `src/client/knownPlayers.ts`) and of its seats are apart: nothing that drops a seat forgets the player, and nothing that forgets the player touches a seat. Only a list of players that did load may say a remembered player is gone.
- The client redraws a part of the screen only when what it shows has changed (`Slot`), so a tap or a half-typed bet survives updates from the server.
- `App` (`src/client/app.ts`) is the screens. `TableConnection` (`connection.ts`) is the conversation with the server about one table: the poll that is kept open, sending commands, the lock on the move buttons, and which of the views that come back is the one to show. It tells `App` what happened through `TableListener` and never touches the page.
- A request that got no answer is not a refusal. Only `unauthorized` or `not_found` may take a player's seat out of the address or the browser's memory; anything else is retried. A table that was put away is `not_found` with `putAway: true`, never a code of its own, so it takes the seat like any `not_found`, also in code that knows nothing of the flag. A move (`MOVES` in `connection.ts`) that got no answer is looked up with a fresh poll, never resent. A reaction or a throw (`FLEETING` there) that got no answer is dropped, neither looked up nor resent, and no answer to one, a refusal included, touches the seat: the poll hears the same and acts on it.
- Every request and every answer carries a build id, so a page from before a deploy can tell. The page asks only through `ServerLine` (`connection.ts`), never `platform.transport`. A host answers only through `BuildGate` (`src/server/build.ts`), and puts the build on any answer it makes up itself (the `internal` failure in `gas/main.ts`). A new operation gets its line in `OPEN_TO_ANOTHER_BUILD`: only one that changes nothing may be asked by a page of another build. Being out of date is `stale`, never `unauthorized` or `not_found`.
- `npm run test:e2e` also runs `scripts/hostedRun.ts`, which puts a stand-in for Apps Script's `google.script` in the page. Changes to how the page starts, remembers a seat or sends requests need a case there.
- A name typed into the create or join form goes on that server's list of players, and a second visitor typing it is refused. In the browser scripts, give each visitor to one server a name of its own.
- Colors, fonts and radii in component CSS come from the tokens in `src/client/styles/tokens.css`, never a literal.
- CSS for a feature is its own file in `src/client/styles/`, with a line in `STYLESHEETS` (`styles/order.ts`), which is the order of the cascade. The build stops on a stylesheet that is not listed.
- A dialog is its own file in `src/client/render/dialogs/` that exports a `DialogKind`, its menu entry (`menu`) beside it, with a line in `REGISTERED` (`dialogs/index.ts`), whose order is the menu's. Dialogs open each other by kind (`handlers.open({ kind: 'ledger' })`), never by import.
- `styles/order.ts`, `dialogs/index.ts` and `effects.ts` are merged as a union (`.gitattributes`): when two branches each add a line at the same place, git keeps both and reports no conflict. Keep every entry and import in them on one line, and check the order of the list after a rebase that touched one.
- A choice a viewer makes for themselves is one entry in `PREFERENCES` (`src/client/prefs.ts`): its control in the Preferences dialog, where it is kept and its `data-` attribute or custom property on the app's element (`css`) follow from the entry. Read it with `prefs.get('sound')`, never from `Memory`.
- Something that happens on the page when the table changes (a sound, an animation, an alert) is a `TableEffect` in `src/client/effects/`, with a line in `TABLE_EFFECTS` (`effects.ts`), never a line in `App`. It reacts to everything its `TableChange` (`tableChange.ts`) hands it, the hand's new events (`events`) and the new chat and play-by-play lines (`feed`), and keeps no record of its own: that is where late, repeated and missed views are dealt with, and where a new list of things that happened gets the same treatment. What must be told once even past a late view (`nightEnded`) is remembered by `TableNews`, beside `tableChange`, never by the effect. What reaches the page more than ten seconds after it happened counts as missed and is handed to no effect, so a browser check lets the page show what happened before it moves the rig's clock on.
- Motion is decoration over a table already drawn as it truly is: it is played through `context.motion`, animates only transform and opacity, never delays a button, and once it lands or is cancelled leaves the page exactly as it is with animations off. What a hand event moves starts in the frame its sound does: `movesSeen` takes its beats from `soundsPlaced`, so the two are timed in one place.
- A field added to what a table saves gets its default in `SAVED_DEFAULTS` (`src/engine/upgrade.ts`), which fills in what a table saved earlier lacks; a setting needs only its registry entry. Any other change to the shape of `TableState` means bumping `STATE_SCHEMA` and adding the step to `upgradeState` that brings a table saved before the change forward. Either way `tests/savedTables.test.ts` must keep passing: it loads the tables older code saved (`tests/fixtures/tables/`) and plays them on.
- What a finished hand came to is `handFacts` (`src/engine/handFacts.ts`), and what happens when a hand ends is an entry in `AT_HAND_END` (`src/engine/handEnd.ts`), handed those facts. Anything that counts, rewards or remembers something about hands hooks in there, never in `hand.ts`, and keeps what it counts small, beside `state.tonight`, and recountable from the hand records. A badge is one entry in `BADGES` (`src/engine/badges.ts`) with its cases in `tests/badges.test.ts`; what a rule needs and the facts lack is counted in `countHand` as a number of its own, never kept by the badge.
- A reaction or a throw is one entry in `REACTIONS` (`src/engine/reactions.ts`), its mark held to the emoji every phone draws (`tests/badges.test.ts`). The table keeps the last few seconds of them in `state.reactions`, written there alone and touching nothing else of the game. The page tells each once as `TableChange.reactions`, its viewer's own at the tap (`ShownTable.react`), and shows only those `sendersShown` (`src/client/senders.ts`) lets through, which is where anything that hides a sender goes. A throw flies as a move in `ASIDE_MOVES` (`src/client/motion.ts`), decoration that `idle()` and `data-moving` leave out, and its whoosh is in `ASIDE_SOUNDS` (`src/client/sound.ts`), played at once outside the queue, so nothing of the game ever waits for one or is pushed back by one.
- `scripts/rig.ts` sets up a table for a browser check with the cards fixed and a clock the check moves, and `scripts/screenChecks.ts` (run by `npm run test:e2e`) has one check per screen that has broken before. A new screen state, or a layout bug that gets fixed, gets a check there: `node scripts/screenChecks.ts "part of its name"` runs one.
- The screen checks run four at a time, each on a rig of its own (`scripts/checkRunner.ts`; `CHECK_WORKERS=1` runs them one by one). So a check never leans on a neighbor: it sets up everything it looks at, and passes alone, in any order and beside any other. What its pages throw fails it, and one still running after 90 seconds is stopped and failed by name, with pictures of its pages in `screenshots/stuck-*.png`.
- A check waits for the page to show or say something, never for a length of time: beside other checks the page may answer a second late. The game's clock stands still until the check moves it (`rig.advance`, or `play` on the table), so no hand plays on under a check that is looking at it. `waitForTimeout` is only for showing that nothing happens, after waiting for what does.
- CI runs the browser tests too, with other fonts than a Mac has, so the buttons under the table wrap differently and the table gets another height and sometimes another shape. `RIG_FONT='Times New Roman' node scripts/screenChecks.ts` (narrower) and `RIG_FONT=Verdana` (wider) show here what fails only there; a check about the table's shape sets its height itself with `setStageHeight`.
- While the last cards of an all-in runout are turned over, `Suspense` (`src/client/suspense.ts`) holds back the end of the hand the same view brought: the whole page is drawn from `suspense.shown(view)` (no result, the pot in the middle, the stacks, the ledger and the night's numbers as they were, the hint and the feed as before the cards) and the effects are told the result once the cards are up, as though a later view had brought it. So everything the table screen draws comes from `App.shownView()`, never from the view as the server sent it, or it gives the result away during the hold. A new part of the view that a hand's result changes joins `Standing` there, or the dialog that shows it does the same.
- The rig's pages keep the table still. A check about motion opens one with `{ moving: true }`, waits on `dealt` (`.stage:not([data-moving]):not([data-chances-pending])`), never on time, and measures it against a still page of the same table (`watch`).
- A hand's chance to win is asked of `chancesOf` with a spot that `spotsOf` makes from the view the page shows, less the cards it still has face down: never from the server's view, and never saved or sent (the README has how it is put together). A figure is drawn only on a table at rest, a moment after the cards even on a still page, so a check that reads a table with hands face up waits on `dealt` first.
- What the table screen shows is worked out in one place, `ShownTable` (`src/client/shownTable.ts`): every view passes `Suspense` and then `PendingMove` on its way to the screen (`App.shownView()`) and to the effects. Another layer between the server's view and the screen goes in that pipeline, never around it.
- A player's own move is shown the moment it goes out, before the server answers. `predict` (`src/client/prediction.ts`) is a pure function of the shown view and the move, built on the engine's own rules (`src/engine/betting.ts`), and claims only what the move itself settles: never a card, a result, or what another player or the server does next. `tests/prediction.test.ts` holds every claim to the engine on random tables, so whatever a prediction comes to claim is added there.
- A view never moves the table backwards under a pending move: one that still has the decision open (`turnOf`, the hand's own number for it, and nothing else) is drawn with the move on it, and the first that does not ends the prediction, whichever request brought it. A refusal and silence stay different: refused, the move comes off and the server's words say why; unanswered, or late, it stays on the table marked (`data-unconfirmed` on `.stage`) until the lookup's view confirms it or puts it back. Nothing sends a move twice, and the effects hear of a move once, when it is made.
- A move reaches the screen one way: `TableConnection.send` tells its listener how the move stands (`move`), and `ShownTable.moveIs` shows it, marks it or takes it off. Whatever makes a move, a tap, a key or a choice made in advance, sends it there and shows nothing itself. A move of the turn shows as played. Any other kind in `MOVES` (`connection.ts`), a pick of how many times to run it or one added later, shows only as sent, its buttons gone until the table has answered, and shows more once `predict` knows it; the buttons of a new kind go in the bar's chain after the `sent` branch (`seatedControls`). A prediction never touches `ledger` or `tonight`: the Tonight and ledger dialogs show the server's numbers until its answer.
- The table is drawn again only when something it draws has changed (`handDrawn` in `src/client/render/table.ts`), so the view that confirms a move draws nothing unless it brings something new, which on a table with an action clock is the next player's clock. Any redraw ends what is still moving, so nothing the table does not draw goes into that comparison.
- A browser check that looks at a page while a request is on its way holds the request with a gate, never a delay: `Gate.on(page, 'moves' | 'polls')` in `scripts/rig.ts`, closed on requests or on answers, waited on with `holding()`, then opened, lost or refused. And since a page shows its own move at the tap, a check that goes on to read the table or act for the next player makes the move with `answeredAfter` (`scripts/pageSpies.ts`), which waits for the server's answer, not for the buttons to go.

## Google side

- `src/gas/sheetStore.ts` talks to the Sheet through small interfaces (`src/gas/sheets.ts`), with fakes in `tests/fakes.ts`. Every write and every cache refill happens under the script lock (`underLock`), which is what keeps the cache from ever being older than the Sheet. The fakes refuse a write, a new tab or a deleted row without it, except in the Errors tab.
- A failure the game carries on through (a `catch` that doesn't rethrow, a request answered `busy`, a step a sweep gives up on) is reported through `ErrorLog` (`src/server/errorLog.ts`), never with `console.error` alone: `failed` in the service, or `HeldReports` (`src/gas/sheets.ts`) in a Sheet store, tells Apps Script's log and the error log in one call (a store's once the lock is let go), and a store that gains a tab reports the same way. A refusal (`invalid`, `unauthorized`, `not_found`) is an answer and is never reported, and neither is a request a page got no answer to. A row is built only from the fields of `ErrorRow`, its message and trace through `scrub`: never from a table's state, a request's body or anything a player typed. Reporting never throws, never waits for the lock, and one script run reports three failures at most.
- The Errors tab is the one tab written without the script lock: its commonest row is the lock not being had, which can't be waited for again. It is only appended to (`appendRow`, which Google keeps apart from other appends) and trimmed from the top, nothing caches it, and its cells are formatted as text when it is made, with a leading apostrophe on any value a Sheet would take for a formula or a number. The fakes allow that only for the tabs named in `lockFree`.
- A new tab of the Sheet is a store of its own: an interface in `src/server` named for what it keeps, with list-save-delete sized to what the service needs and the rule shared by both implementations beside it (`PresetStore` and `placeOf` in `presetStore.ts`); a memory implementation for `npm run dev`, the rig and the tests; and the Sheet's in `src/gas`, built on `openTab` and `underLock`. The deployed Sheet already exists, so the tab is made by `openTab(..., true)` on the first write, under the lock, and reading a Sheet without it is reading nothing. A row someone broke by hand is skipped, never fatal. Its limits go in the fakes (`rowLimits` for a cap on rows) and its tests in `tests/sheetStore.test.ts`, run against both implementations where the behavior is shared. Wire it in `src/gas/main.ts` and `ServiceDeps`.
- The fakes enforce the limits that bite (50,000 characters a cell, 100 KB a cache value, 250 characters a cache key); give them any new limit the store comes to depend on.
- A table leaves the Tables tab only in `SheetStore.sweep`, asked for only by `PokerService.putAwayOldTables`. It never throws, waits a second at most for the lock and makes a bounded number of calls, which `tests/sheetStore.test.ts` counts and fails one at a time (`Calls` in the fakes). A table is in the Archive, flushed, before anything of it is taken from Tables. A row is emptied, never deleted or moved: a row number in the cache is then only ever wrong for its own table, and `locate` checks the id it finds there. A row with no readable Updated time is new, never old.
- Ledger entries and hand records are saved in the table's row with the state, then copied to their tabs. Only the write of that row may fail a request.
- A table's rows in the Results tab are made by `resultsOf` alone and written by `ResultWriter.write`, which replaces them: never append to that tab, and never count a night any other way. Only a store of tables writes there, holding the script lock, and nothing it writes there may fail a request.
- Nothing reads the Results tab by a header, and the standings hold only what the page shows: no table id, member id or token.
- Creating or joining a table never fails because of the Players tab: the player gets in with no identity when the list can't be read or written, has no such player or is full (`arrival` and `enlisted` in `src/server/service.ts`). Only a new name the list already has is refused. Each step an arrival goes ahead without runs through `without`, which reports a failure by the step's name and never an answer (a full list, a name taken meanwhile). The table lets someone new in before the list is written to, never the other way around, so nobody is on the list for a request that came to nothing.
- The owner edits the Players tab by hand. `SheetPlayerStore` reads it by position from one `getValues`, never by a header, skips a row it can't read without repairing it, and formats every cell before writing to it. Its cache entry is short-lived because a hand edit tells the cache nothing.
- Apps Script strips what it reads as comments from the page's inline scripts, and reads a `//` inside a template literal as one. `scripts/bundle.ts` ships the script with no `//` or `/*` in it and fails the build when it can't; the stand-in in `tests/appsScriptBundle.test.ts` strips the same way.
- `.clasp.json` and `.deployment.json` are per machine and ignored by git.
